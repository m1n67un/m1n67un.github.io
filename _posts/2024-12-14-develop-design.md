첫번째, 두번째 회사를 지나고, 세번째 회사는 첫번쨰 직장의 이사급 임원분의 창업으로 기회가 되어 스타트업으로 들어갔다.

스타트업에서 근무를 하게되다 보니, 마케팅, 운영팀을 제외한 적은 인원의 개발팀으로 구성(2명)되어어 운용 중이다 보니, 혼자서 데브옵스, 풀스텍 개발자로 일을 연속적으로 하게되는 경우가 많았다.

올해 초 다수의 팀원들을 끌고, 프로젝트를 진행해본 경험이 없어, 약간 맨땅에 헤딩하는 느낌이 있었지만, 10인 정도의 팀원이 투입된 프로젝트(`도서 콘텐츠 플랫폼`)의 PL 역할을 맡게되고 좋은 기회를 맞아, 화면 설계 시점에도 투입되지 않고, 기획자가 급작스럽게 2주만에 빠지는 상황이 생겨, 설계를 맞출 시간도, 총 프로젝트 기간은 1년이였지만, 개발 기간은 2달이라는 시간이 주어져, 정말 짧은 상황에 모두 개발 완료가 되어야하는 상황에 어찌어찌 대응으로 잘 이끌고 나가게되어서 마무리 되었다.

2024년 12월 12일. 새로운 프로젝트의 PL 역할을 맡아야할 일이 생겼다. 
이번 프로젝트는 `상품 판매 플랫폼` 이라고 보면 된다.

사실, 프로젝트 개발 문서를 형식적으로는 고객사들에게 넘겨주기 위해 만들었던 기회는 개발자들에게 많이 있을 수 밖에 없다.
하지만, 이번 프로젝트는 조금 특이하게, 개발 문서 초안들을 모두 작성하는 과정정까지는 그저 일반적인 프로젝트와 다름이 없지만, 개발자들이 개발 문서 만을 보고, 개발을 할 수 있는 환경을 구성하면서 병행하여, 개발 문서들을 작성해야 한다.

**여기까지가 서론이다.**

## STEP 1. 기능정의서 작성

시작하기 앞서, <kbd>요구사항정의서</kbd>와 <kbd>IA(정보구조도)</kbd> 그리고 <kbd>화면설계서</kbd> 는 전달받아서, <kbd>기능정의서</kbd>부터 작성을 시작하였다.

#### - FO 피그마 내용
![FO](/assets/img/2024/km-figma-fo.png){: w="700" h="400" }

#### - BO 피그마 내용
![BO](/assets/img/2024/km-figma-bo.png){: w="400" h="700" }

위 화면에 있는 갯수가 생각보다는 많긴하지만, 플랫폼이 운영하기에 그렇게 많은 화면 갯수가 아닐 수도 있다.

처음으로 작업을 시작한 것은 BO 화면부터 시작하였다.
최상단에 있는 <kbd>로그인</kbd>, <kbd>회원 관리</kbd> 부터 작업을 진행하려 한다.

이번에 작성하려는 기능정의서는 빠르게 확인할 수 있는 번호 부여 **NO**, 고유한 **기능 ID**, 설계서에 작성되어 있는 **화면 번호**, **기능 그룹**, **기능 분류**, **기능분류영문**, **기능명**, **채널**, **마이크로명**, **도메인명**, **기능설명**, **기능발현위치** 등 으로 구성하여 작성할 예정이다.

마이크로명(?), 도메인명(?) 등이 왜 필요하냐 라고 생각할 수도 있지만, 우리는 멀티모듈 모놀로식 구조에서 MSA 구조로 사내 전체적으로 전환작업을 진행 중에 있다.

---

쉽게 알기 위해 설명하자면:

##### - 멀티모듈 모놀로식
```
+-------------------+
|   Application     |
|-------------------|
|  +-------------+  |
|  | Common      |  |
|  +-------------+  |
|  | Module A    |  |
|  +-------------+  |
|  | Module B    |  |
|  +-------------+  |
|  | Module C    |  |
|  +-------------+  |
+-------------------+
```
- 멀티모듈 모놀리식 아키텍처는 하나의 애플리케이션 내에서 여러 개의 모듈로 구성됩니다. 각 모듈은 특정 기능이나 도메인에 따라 나뉘어 있으며, 일반적으로 공통 모듈을 통해 의존성을 관리한다.

##### - MSA
```
+---------------------+
|     API Gateway     |
|---------------------|
| +------+ +------+   |
| | Service A |      |
| +------+ +------+   |
| | Service B |      |
| +------+ +------+   |
| | Service C |      |
| +------+ +------+   |
+---------------------+
```
- MSA는 여러 개의 독립적인 서비스로 구성되어 있으며, 각 서비스는 특정 도메인 또는 비즈니스 기능을 수행, 이 서비스들은 API 게이트웨이를 통해 상호작용한다.

> 일반적인 규모 에서는 모놀로식 구조로 개발하는 것이 보편적이다. 대규모 트래픽을 요하거나, 조직이 매우 큰 경우, MSA 사용하면 좋다.

### **기능정의서** 작성 방식
- 작성에 앞서, 어떤 프로세스로 작성해야할지 아래 내용들을 확인한다.

![alt text](/assets/img/2024/km-admin-manage-bo.png){: w="700" h="400" }
> 위 이미지는 BO 수많은 화면 중 `관리자 관리` 화면이다.

`관리자 관리` 화면 중 그리드 에서 **총 7개의 필드**(NO, 권한, 이름, 아이디, 연락처, 생성일, 최근 접속일) 이 있는 것을 확인하고, 해당 내용들을 그대로 기능정의서에 옮겨볼 것이다.

---
기능정의서는 위에서 작성한 내용대로 `No`, `기능ID`, `화면 번호`, `기능 그룹`, `기능 분류`, `기능분류영문`, `기능명`, `채널`, `마이크로명`, `도메인명`, `기능설명`, `기능발현위치` 정도로 문서 양식의 헤더를 작성하였다.
![alt text](/assets/img/2024/km-fs-blank.png){: w="700" h="400" }
> 위 이미지는 기능정의서 양식의 빈 공란의 내용들이다.

내용을 하나씩 채워볼 예정인데, `기능ID`부터 어떻게 작성할 지 확인해본다.
